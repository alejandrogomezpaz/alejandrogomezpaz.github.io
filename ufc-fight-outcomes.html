UFC Explainable Fight Outcome Website

My experience building a counter-factual classification model with confidence quantification and natural language reasoning.

Python Playwright BeautifulSoup PostgreSQL scikit-learn Glicko-2 Elastic Net
Try the live site View source

Motivation

I love to wrestle and this became a new love for combat sports because of their complexity and creativity. In college, I made a friend who loved UFC and MMA. We started watching fights together and ended up betting money on two fights. I lost both :(

This inspired me to:

  1. Make a model that gives me a prediction on who will win;
  2. Teach me about what factors really matter in MMA and how stylistic matchups work;
  3. Teach me how to build a real-world model.

Data Acquisition

Starting off with the data, I searched for a while: Kaggle, Hugging Face, GitHub repos, to no avail for a large complete database. And so I decided to scrape the data from where the UFC sources their data: ufcstats.com.

I started off with BeautifulSoup requests and started trying to configure how to scrape the fights, fighter stats, and fight–fighter matchups. I settled on a tree architecture visualized below.

Events page Fighters lookup page │ │ └─► event URLs └─► fighter URLs │ │ └─► fight URLs └─► fighter stat tables │ └─► fight stat tables

Unfortunately, in an early debugging-phase run, I requested enough page HTML to be blacklisted from their website — this is to mean that they asked my browser to solve a JavaScript problem that BeautifulSoup could not solve. After talking to my friend who had faced similar problems at a previous internship, he suggested I try out Playwright, a browser manipulation Python library.

The tradeoff

Using Playwright adds much run time due to the built-in buffer times between page creation and usage. In order to combat this I configured a function to run many browsers in parallel: a very simple use case of multithreading.

After configuring my BeautifulSoup pipeline with an initial Playwright URL→HTML parser, and some fail-safes and redundancies to catch any errors, I ran my data scraping pipeline which saved the data to CSV files.

URL ──► Playwright (parallel browsers) ──► HTML ──► BeautifulSoup ──► CSV

Data Cleaning

Beyond a simple exploratory data analysis and deduping / data-type casting, the main obstacle in this stage was how to design the data in such a manner that:

  1. Important data was preserved;
  2. Duplicate data is not saved across different tables;
  3. Each table served a unique purpose in the creation and querying of a model;
  4. The schema was minimalist.

After a lot of thinking I settled on a three-table schema.

TablePurpose
fighterFeatures for model querying
fightModel training, because it was labeled
fighter–fightLookup table

Upon running a simple logistic regression model on this initial fight table I received a 93% test accuracy score. Since this is impossibly good, obviously something was wrong. Apparently a feature included was the record, which was a huge leak in the data. Also, the lifetime aggregate stats for each fighter presented (although less) data leakage.

The fix

In order to fix this I decided on a primary key of fighter–date, composed of data only available before the fighter on said date, and aggregated data this way.

Model

Given that fighters present different strengths and performance consistency, I wanted to try out a rating system. The Elo system was attractive because of the simplicity, but it didn't provide a consistency factor. I read a research paper on the Glicko system which did account for this, and chose to proceed with the Glicko-2 system.

Upon constructing a fighter–date rating table, the test accuracy was really low: only a 4% edge over guessing. I believe this is because:

  1. The UFC constructs fights to be roughly even, because that is what sells;
  2. The stylistic matchup;
  3. High volatility of MMA.

Instead I came back to the logistic model, but now with time-normalized, dataset-normalized feature differentials between fighters with the included ratings.

But which logistic model? Given the extremely correlated / collinear relationships of the data and the motivation for simple factors, I tried the elastic net (L1, L2) logistic model and tuned the λ₁–λ₂ penalty coefficient ratio. Interestingly, this actually converged to the L1 logistic model when optimizing the training accuracy.

min − Σᵢ [ yᵢ log pᵢ + (1−yᵢ) log(1−pᵢ) ] + λ₁∥β∥₁ + λ₂∥β∥₂² where pᵢ = σ(βᵀ xᵢ), xᵢ = feature differential (fighter A − fighter B) tuning the λ₁:λ₂ ratio ──► converged to pure L1

Website Serving

I saved the trained logistic model to a .joblib file in order to minimize storage, and instantiated a hosted database in PostgreSQL.

Given that new UFC fights happen all the time, I also created a self-updating feature that scrapes, cleans, appends, reruns the Glicko-2 ratings, and updates the database each UFC event.

each UFC event │ ├─► scrape ├─► clean ├─► append ├─► rerun Glicko-2 ratings └─► update database ──► site serves fresh predictions

Then I Clauded the UI of the new website, since I was not interested in learning how to do it rather than just having the final product.

See it live

The finished site is up at ufc-elo-system-en5j.vercel.app — pick two fighters and it returns a prediction, updated after every UFC event.
