Building an Offline Retrieval-Augmented Generation Pipeline

Rebuilding a prototype RAG system into a production pipeline for embedded safety advice — and figuring out how to prove it actually got better.

LLMs Optimization Databases Python Embedded AI

Motivation

I joined the SEAL lab team working on RAD-AI: an embedded AI product that gives natural-language safety advice to non-expert emergency responders, derived from raw sensor data.

I had just finished a deep learning series and was deep into how LLMs work mechanistically. The team's spring report flagged full retrieval-augmented generation as the most consequential direction available: a minimal viable RAG prototype already existed, but what the product needed was a custom, production-ready system.

What RAG Actually Is

Before the technical part, the non-technical brief:

LLMs hallucinate. They misremember, or they invent outright. That's bad in general and dangerous when the output is safety advice.

The fix is to stop the model from answering off the top of its head. Think of someone who needs advice: instead of guessing, they go to a librarian, who hands back the few most relevant books. They read those, and answer from them. That's retrieval-augmented generation.

There are two halves:

  1. Database instantiation — building the library and sorting the books. Done once, takes a while.
  2. The query pipeline — the librarian fetching the specific books the model needs. Every query, has to be fast.
DATABASE (once) scrape ──► clean ──► chunk ──► index QUERY (every time) embed query ──► rank ──► retrieve + system prompt ──► generate

My Work

I started by reading the original Retrieval-Augmented Generation paper, some lectures on interpretability, and then the prototype code the team had written.

The prototype worked, but there was room for improvement at every stage. A clear example: it split every document at exactly 2,200 characters with a 300-character overlap. That does two bad things at once — it stores duplicate text, and it cuts through the middle of ideas. Both degrade retrieval quality, and the system compensates by spending a bigger token budget.

The Question I Couldn't Answer

Early on I was explaining the project to my brother and he asked an obvious question: how do you know the RAG is getting better?

I didn't have an answer.

Answering it properly took a few papers — the most helpful being one on RAG for nuclear-domain question answering — and a fair amount of thinking about what "good" even decomposes into. I landed on six metrics:

MetricWhat it captures
Tokens per queryContext budget spent to answer
LatencyWall-clock time to first usable answer
Retrieval qualityDid the right chunks make the shortlist
Answer correctnessVerified against a written answer key
HallucinationClaims unsupported by retrieved sources
Refusal accuracyDeclining exactly when it should

The whole thing is a multi-variable optimization, and the variables trade against each other. More retrieved chunks means better recall and more tokens. A better re-ranker means better answers and more latency.

The Hard Part: Hallucination

Hallucination isn't a regular expression. Judging whether a model made something up requires a judge that understands the claim, the source, and the gap between them.

I automated it with API calls to a third-party LLM with a large context window, given a purpose-built judging prompt — then human-validated a sample of its verdicts as a second layer. Every benchmark run is logged to a readable file, so a domain expert can audit any individual call.

One caveat

Hallucination rate measures the RAG and the LLM together. A refusal-capable RAG lowers it, but you are never measuring the retrieval system in isolation.

The Corpus Problem

Before writing a line of pipeline code, I found something I wasn't looking for: the existing corpus was poor. The documents were unrelated to the product — legal filings, political text, nothing that could answer a real user question.

So the benchmark had a prerequisite I hadn't planned for. I had to iteratively scrape a corpus large and relevant enough to make benchmarking the RAG meaningful in the first place.

Database Design

Ingestion. A folder of PDFs, with a seamless add-on path so users can drop in their own local documents — versus the prototype's rigid ingestion.

Semantic structure-aware chunking. Instead of cutting at a fixed character count, the chunker walks the document measuring semantic similarity between adjacent spans. When similarity drops below a threshold, it cuts there. The output is chunks that are complete ideas with no duplicated text, which optimizes both memory and retrieval quality.

Two backstops handle the tails: chunks that come out too small get merged with neighbors, and chunks that come out too large get recursively re-split.

text ──► span similarity ──► below threshold? ──► cut │ too small ────┼──── too large │ │ merge recurse

Citations. Because chunking respects document structure, the metadata survives the split — so each chunk carries a verifiable citation instead of a guess about where it came from. That matters: validation is only possible if a human can trace a claim back to a page.

Indexing. I chose ChromaDB for lightweight vector storage, leveraging Hierarchical Navigable Small World (HNSW) indexing — O(log n) search as opposed to flat search's O(n).

Retrieval

The core change is a two-stage ranker.

  1. Stage 1 — cosine similarity between the embedded query vector and the chunk vectors: a fast, approximate filter down to a candidate set.
  2. Stage 2 — a computationally expensive re-ranker running a full-attention cross-encoder over the query and each individual candidate.

This works because stage 1 compares frozen vectors: each chunk is embedded independently of the query, so the score only measures topical proximity. An on-topic chunk that lacks the answer ranks as highly as one that contains it. Stage 2 reads the query and the chunk together, which separates "about this" from "answers this" — but costs far more per pair. Hence the ordering: cheap recall over the corpus, expensive precision over the shortlist.

stage 1: cos(q, cᵢ) = (q · cᵢ) / (∥q∥ ∥cᵢ∥) ──► top-k stage 2: sᵢ = f(concat(q, cᵢ)) ──► top-n, n ≪ k

Refusal threshold. If even the best-scoring chunk is weak, the system declines to answer instead of handing over the closest book anyway. The prototype had no such threshold. No answer beats a wrong answer — especially for safety advice.

System prompt. Rewritten, and the chunking tuned jointly with it for token efficiency. Attention cost grows faster than the text does, so every token you don't send saves disproportionate time and compute.
